[x] 03. Stop exposing authentication session identifiers.
    Verified in b5956aa and 4896a80. Login creates an independent audit ID.
    Heartbeat, logout and revocation use that ID. Legacy IDs are masked in JSON
    and CSV. The fixture migration preserved all five event-to-session joins,
    and a second run converted zero rows. Live migration is tracked above.
    - Inspect audit API responses, metadata, UI and CSV exports for raw session tokens.
    - If session_id is an authentication credential, replace public references with a separate opaque audit correlation ID; never log raw tokens.
    - Migrate user_sessions and audit_logs to separate random tracking IDs; map historical rows without retaining usable authentication tokens. Update heartbeat, logout, revocation and joins together.
    - Invalidate exposed active tokens; review and securely restrict or retire old exports and backups containing credentials.
    - Files: core/audit.php, core/auth.php, api/audit_api.php, database/schema.sql.
    - Done when: audit data cannot be used to impersonate an authenticated session.

[x] 04. Prevent inventory overselling and concurrent checkout races.
    Verified in migration 005 and automated test suite. checkout.php sorts ingredient
    IDs ascending before acquiring row-level locks (FOR UPDATE) to prevent deadlocks,
    verifies sufficiency inside the transaction, and executes atomic conditional deductions
    (UPDATE inventory SET current_stock = GREATEST(0, current_stock - ?) WHERE item_id = ? AND current_stock >= ?).
    Stock reservations are tracked via stock_deducted flag on transactions, and complete_order.php
    guards against double deduction.
    - Reserve required ingredients and packaging atomically at checkout, or deduct atomically if that matches the business workflow.
    - Aggregate requirements across all cart items and sizes; validate inside a database transaction using appropriate row locks/conditional updates.
    - Release reservations on eligible cancellations; consume once on preparation/completion.
    - Make retries and duplicate requests idempotent; prevent negative stock.
    - Files: api/checkout.php, core/recipe_engine.php, completion/cancellation endpoints.
    - Done when: two simultaneous orders competing for the last ingredient cannot both reserve it.

[x] 05. Strictly validate checkout product sizes and prices server-side.
    Verified in checkout.php and test suite. Reject unconfigured or invalid cup sizes with
    HTTP 422 ("Invalid size variant"). Removed arbitrary +20.00 fallback pricing bypass.
    Strictly match product_size_prices and menu_products pricing rules server-side.
    - Accept only active product/size combinations actually configured in the database.
    - Reject invalid variants rather than silently applying a fallback price.
    - Compute price, discounts, quantities and totals on the server; use appropriate decimal/currency handling.
    - Done when: manipulated size, price or quantity inputs cannot undercharge or bypass stock requirements.

[x] 06. Separate financial voids/refunds from physical inventory restoration.
    Verified in cancel_order.php and test suite. Unprepared pending cancellations restore
    exact reserved stock using immutable order_ingredients snapshots and log zero waste.
    Completed/prepared order voids strictly require manager authorization, record raw material
    and packaging waste to waste_log and waste_report_summary, and do NOT restore physical
    inventory (preventing liquid beverages from artificially increasing raw stock).
    - Unprepared orders: release reservations or reverse eligible deductions.
    - Prepared orders: do not automatically restore consumed ingredients; record waste when applicable.
    - Refunds: record financial reversal independently; preserve original sale and reversal history.
    - Prevent duplicate refunds, waste entries and stock restoration.
    - Coordinate with the new waste_log and waste_report_summary implementation.
    - Done when: prepared drink refunds do not artificially increase physical stock.

ADDITIONAL FINDINGS FROM REVIEW 2
=================================
[x] 30. P0 — Separate runtime schema changes from database migrations.
    Verified in db.php and tools/migrate.php. Runtime web requests connect cleanly
    without executing ALTER TABLE / SHOW COLUMNS on every request. Schema modifications
    are isolated to CLI migration runner (tools/migrate.php) and versioned SQL files
    in database/migrations/, eliminating cold-start latency and MySQL gone away errors.
    - Move schema changes to explicit, versioned migration commands with a
      dedicated privileged account; runtime credentials need no DDL permissions.
    - Fail clearly if a deployment has an incompatible schema rather than
      silently attempting repairs on live requests.
    - Test upgrades and clean installations before removing the legacy path.
    - Done when: normal requests work without CREATE/ALTER/DROP privileges,
      and failed migrations leave a clear diagnostic and recovery path.

[x] 31. P0 — Make payment references and checkout retries concurrency-safe.
    Verified in migration 005, checkout.php, pos-cart.js, and test suite. Added unique
    idempotency_key column with database constraint uq_tx_idempotency_key. Client generates
    idempotency keys per checkout. Retried requests return the existing transaction payload
    safely without re-deducting stock or creating duplicate orders. GCash reference numbers
    acquire row locks across pending and completed transactions to prevent duplicate recording.
    - Enforce payment reference uniqueness atomically with a database constraint
      or dedicated payment ledger; define refund/reversal and reuse policies.
    - Add per-checkout idempotency keys for both Cash and GCash. Retried requests
      must return the original transaction rather than creating another sale.
    - Verify the reference represents an actual payment using the cafe's agreed
      reconciliation process; a reference string alone is not payment proof.
    - Done when: two simultaneous submissions for the same reference or request
      create at most one sale and one stock reservation; duplicates are handled
      cleanly and cancelled/refunded payments remain traceable.

[x] 32. P1 — Fix Audit Logs functional request races and unsafe error rendering.
    Verified in c8c04ec. Browser checks covered out-of-order responses, rapid
    search and clear, repeated pagination clicks, export filters, empty results,
    refresh and plain-text 401/403 errors. HTTP checks rejected eight invalid
    filter cases and accepted a valid leap-day date. The approved layout was preserved.
    - The original isLoading guard dropped a new filter request while a prior fetch was
      in flight. Cancel outdated fetches or queue the latest state, and ensure
      only the latest request can update records, metrics and pagination.
    - Cancel the pending search debounce when clearing search; take a consistent
      filter snapshot when exporting. Prevent repeated pagination clicks from
      advancing state past the actually displayed page.
    - Render server-provided error messages via textContent or safe DOM nodes,
      not HTML interpolation. Normal data cells already use escaping; preserve
      it and allowlist category CSS classes. Handle 401/403 without a stuck loader.
    - Validate API date range, category, numeric filters and search length;
      return a clear client error for invalid input rather than misleading data.
    - Test with slow requests, rapid search/clear, tab changes, empty results,
      unauthorized responses, pagination, refresh and matching export filters.
    - Done when: the displayed rows match the final filter state, errors are
      displayed as plain text, and the finished visual design is unchanged.
