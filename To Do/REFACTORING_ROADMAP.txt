1.1 API Middleware Pipeline (`core/api_bootstrap.php`)
--------------------------------------------------------------------------------
CURRENT STATE:
While `api/predictive_api.php` has already been slimmed down to 37 lines using
`core/predictive_engine.php`, the other 18 scripts in `api/*.php` still repeat
boilerplate for:
- Requiring `core/db.php`, `core/auth.php`, and `core/audit.php`
- Calling `require_role()` or `require_login()`
- Checking HTTP method (`require_method()`)
- Decoding JSON request bodies (`read_json()`)
- Validating CSRF tokens (`require_csrf()`)
- Wrapping execution in `try / catch (Throwable $e)` blocks

TARGET FILES (19 Endpoints in `api/`):
- `api/checkout.php` (419 lines)
- `api/complete_order.php` (191 lines)
- `api/cancel_order.php` (207 lines)
- `api/products_api.php` (578 lines)
- `api/inventory_api.php` (252 lines)
- `api/manual_waste.php` (245 lines)
- `api/accounts_api.php` (453 lines)
- `api/auth_api.php` (618 lines)
- `api/2fa_api.php` (286 lines)
- `api/audit_api.php` (374 lines)
- `api/waste_api.php` (537 lines)
- `api/report.php` (676 lines)
- `api/transactions_api.php` (291 lines)
- `api/predictive_api.php` (37 lines - already delegates to `core/predictive_engine.php`)

SOLUTION:
Create a centralized API pipeline helper in `core/api_bootstrap.php`:

```php
<?php
// core/api_bootstrap.php
declare(strict_types=1);

require_once __DIR__ . '/db.php';
require_once __DIR__ . '/auth.php';
require_once __DIR__ . '/audit.php';

function api_endpoint(array $options, callable $handler): void {
    $method = strtoupper($options['method'] ?? 'POST');
    require_method($method);

    // Authentication & RBAC checks
    if (!empty($options['role'])) {
        $user = require_role($options['role']);
    } elseif (!empty($options['auth'])) {
        $user = require_login();
    } else {
        $user = current_user();
    }

    // Read payload
    $body = ($method === 'POST') ? read_json() : $_GET;

    // CSRF verification for state-modifying requests
    if (!empty($options['csrf'])) {
        $csrf = $body['csrf_token'] ?? ($_SERVER['HTTP_X_CSRF_TOKEN'] ?? null);
        if (!validate_csrf_token($csrf)) {
            fail(403, 'CSRF security token invalid or missing.');
        }
    }

    try {
        $result = $handler($body, db(), $user);
        send_json(array_merge(['success' => true], (array) $result));
    } catch (Throwable $e) {
        error_log('[CafeFlow API Error] ' . $e->getMessage());
        $code = ($e->getCode() >= 400 && $e->getCode() < 600) ? (int)$e->getCode() : 500;
        fail($code, $e->getMessage() ?: 'An unexpected internal error occurred.');
    }
}
```

3.1 Pub/Sub Event Bus (`CafeFlow.events`)
--------------------------------------------------------------------------------
CURRENT STATE:
Theme switching already uses a custom DOM event (`window.addEventListener('cafeflow:themechange', ...)`),
which works cleanly across `reports.js`, `waste.js`, and `predictive.js`.
However, data mutations in `inventory.js`, `products.js`, `pos-cart.js`, and
`pos-queue.js` still call other modules directly via global namespace checks:
```javascript
if (window.CafeFlow.products && window.CafeFlow.products.loadSupplyList) {
    await window.CafeFlow.products.loadSupplyList();
}
if (window.CafeFlow.menu && window.CafeFlow.menu.loadMenu) {
    window.CafeFlow.menu.loadMenu();
}
```

SOLUTION:
Standardize on a lightweight Event Bus in `assets/js/core/utils.js`:
```javascript
window.CafeFlow.events = {
  on: (event, handler) => {
    window.addEventListener(`cafeflow:${event}`, (e) => handler(e.detail));
  },
  emit: (event, detail = {}) => {
    window.dispatchEvent(new CustomEvent(`cafeflow:${event}`, { detail }));
  }
};
```
Standard events to adopt:
- `cafeflow:themechange` (already active)
- `cafeflow:inventory:changed`
- `cafeflow:products:changed`
- `cafeflow:order:created`
- `cafeflow:order:updated`
