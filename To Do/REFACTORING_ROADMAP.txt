1. BACKEND ARCHITECTURE & API LAYER
================================================================================

--------------------------------------------------------------------------------
1.1 API Middleware Pipeline
--------------------------------------------------------------------------------
PROBLEM:
Every single script in api/*.php currently repeats 15-30 lines of boilerplate:
- Requiring core/db.php and core/auth.php
- Calling require_role() or require_login()
- Checking request method
- Decoding JSON body
- Validating CSRF tokens
- Wrapping code in repeated try/catch blocks

TARGET FILES:
- api/checkout.php
- api/complete_order.php
- api/cancel_order.php
- api/products_api.php
- api/inventory_api.php
- api/accounts_api.php
- api/waste_api.php
- api/report.php

SOLUTION:
Create a centralized API pipeline helper in `core/api_bootstrap.php`:

```php
<?php
// core/api_bootstrap.php
require_once __DIR__ . '/db.php';
require_once __DIR__ . '/auth.php';

function api_endpoint(array $options, callable $handler): void {
    $method = strtoupper($options['method'] ?? 'POST');
    require_method($method);

    // Authentication & Authorization checks
    if (!empty($options['role'])) {
        require_role($options['role']);
    } elseif (!empty($options['auth'])) {
        require_login();
    }

    // Read payload
    $body = ($method === 'POST') ? read_json() : $_GET;

    // CSRF verification for state-modifying requests
    if (!empty($options['csrf'])) {
        $csrf = $body['csrf_token'] ?? ($_SERVER['HTTP_X_CSRF_TOKEN'] ?? null);
        if (!validate_csrf_token($csrf)) {
            fail(403, 'CSRF security token invalid or missing.');
        }
    }

    try {
        $result = $handler($body, db());
        send_json(array_merge(['success' => true], (array) $result));
    } catch (ApiError $e) {
        fail($e->getCode() ?: 422, $e->getMessage());
    } catch (Throwable $e) {
        error_log('[CafeFlow API Error] ' . $e->getMessage());
        fail(500, 'An unexpected internal error occurred.');
    }
}
```

BEFORE (api/cancel_order.php):
~160 lines filled with repeated boilerplate, manual transaction handling, and 
manual error decoding.

AFTER (api/cancel_order.php):
```php
<?php
require_once __DIR__ . '/../core/api_bootstrap.php';
require_once __DIR__ . '/../services/OrderService.php';

api_endpoint(['role' => ['barista', 'manager'], 'csrf' => true], function ($body, $pdo) {
    $txId = as_int($body['transaction_id'] ?? null, 1, 4294967295);
    $reason = trim((string)($body['reason'] ?? ''));
    if (!$txId) fail(422, 'Invalid transaction ID.');
    if (strlen($reason) < 3) fail(422, 'Valid reason required (3-255 characters).');

    $user = current_user();
    return OrderService::cancelOrVoidOrder($pdo, $txId, (int)$user['user_id'], $user['role'], $reason);
});
```

--------------------------------------------------------------------------------
1.2 Database Schema Separation
--------------------------------------------------------------------------------
PROBLEM:
In `core/db.php` (Lines 24-280), the function `ensure_schema()` runs on runtime
requests. It executes `SHOW COLUMNS FROM ...` and conditional `ALTER TABLE ...`
queries on live requests. Under heavy traffic, DDL queries cause table locks 
and degrade POS responsiveness.

SOLUTION:
1. Extract all table alterations into a dedicated migrations folder:
   - `database/migrations/001_initial_schema.sql`
   - `database/migrations/002_add_2fa_and_recovery.sql`
   - `database/migrations/003_add_waste_summary.sql`
2. Create a CLI runner in `tools/migrate.php` to run pending migrations once.
3. Remove `ensure_schema()` from `core/db.php`, leaving `db()` as a pure, fast 
   PDO singleton.

--------------------------------------------------------------------------------
1.3 Service / Domain Layer Extraction
--------------------------------------------------------------------------------
PROBLEM:
Financial math, inventory deductions, recipe consumption, and database updates 
are mixed directly inside procedural API scripts.

SOLUTION:
Create domain services in a new `services/` directory:
- `services/OrderService.php`:
  * createOrder($cart, $paymentMethod, $discount)
  * completeOrder($transactionId)
  * cancelOrVoidOrder($transactionId, $userId, $userRole, $reason)
- `services/InventoryService.php`:
  * verifySufficiency($aggregatedConsumption)
  * deductStockForOrder($pdo, $items)
  * restoreStockForOrder($pdo, $items)
  * logManualWaste($pdo, $data)
- `services/ReportService.php`:
  * getSalesReport($period, $startDate, $endDate)
  * getWasteAnalytics($period, $startDate, $endDate)

--------------------------------------------------------------------------------
3.1 Pub/Sub Event Bus
--------------------------------------------------------------------------------
PROBLEM:
Modules currently have tight, brittle coupling. For instance, in `inventory.js`:
```javascript
if (window.CafeFlow.products && window.CafeFlow.products.loadSupplyList) {
    await window.CafeFlow.products.loadSupplyList();
}
if (window.CafeFlow.menu && window.CafeFlow.menu.loadMenu) {
    window.CafeFlow.menu.loadMenu();
}
if (window.CafeFlow.queue && window.CafeFlow.queue.pollQueue) {
    window.CafeFlow.queue.pollQueue();
}
```

SOLUTION:
Add an Event Bus inside `assets/js/core/utils.js`:
```javascript
window.CafeFlow.events = {
  on: (event, handler) => {
    window.addEventListener(`cafeflow:${event}`, (e) => handler(e.detail));
  },
  emit: (event, detail = {}) => {
    window.dispatchEvent(new CustomEvent(`cafeflow:${event}`, { detail }));
  }
};
```

Usage across modules:
```javascript
// In inventory.js (when stock or item is deleted/updated):
window.CafeFlow.events.emit('inventory:changed');

// In products.js:
window.CafeFlow.events.on('inventory:changed', () => loadSupplyList());

// In pos-menu.js:
window.CafeFlow.events.on('inventory:changed', () => loadMenu());

// In pos-queue.js:
window.CafeFlow.events.on('inventory:changed', () => pollQueue());
```

4. CSS & DESIGN SYSTEM OPTIMIZATION
================================================================================

--------------------------------------------------------------------------------
4.1 Consolidating reports.css (3,427 lines)
--------------------------------------------------------------------------------
PROBLEM:
- Over 3,400 lines in a single CSS file.
- Contains 15+ separate `@media` blocks with overlapping breakpoints (max-width: 
  1280px, 1024px, 860px, 768px, 720px, 480px) scattered throughout the file.
- Redundant table, badge, and button styles that duplicate `base.css` and `modals.css`.

SOLUTION:
1. Consolidate media queries to standard variables:
   - Mobile: `@media (max-width: 480px)`
   - Tablet: `@media (max-width: 768px)`
   - Laptop: `@media (max-width: 1024px)`
2. Extract reusable components:
   - `.kpi-card`, `.stat-pill`, `.chart-card` -> Move to `assets/css/components/analytics-cards.css`.
3. Eliminate `!important` tags where proper selector hierarchy can be used.

--------------------------------------------------------------------------------
4.2 Enforcing Unified Design Tokens
--------------------------------------------------------------------------------
PROBLEM:
Some components still feature hardcoded color hexes (`#162318`, `#2d5a27`, `#e8623a`,
`#d48b38`, `#fbf8f2`) instead of theme variables.

SOLUTION:
Run a project-wide search-and-replace to ensure all components reference variables.css:
- `#162318` -> `var(--bg)` / `var(--espresso)`
- `#2d5a27` -> `var(--green)` / `var(--accent-green)`
- `#e8623a` -> `var(--caramel)` / `var(--orange)`
- `#fbf8f2` -> `var(--canvas)` / `var(--cream)`
- `#e5dfd5` -> `var(--line)`

5.1 Migrating Hardcoded PHP Arrays to MySQL BOM Tables
--------------------------------------------------------------------------------
PROBLEM:
In `core/recipe_engine.php` (Lines 14-250), `RECIPE_PROFILES`, `RECIPE_CUP_SIZES`,

database via the UI.

SOLUTION:
1. Write a one-time migration script `tools/seed_recipes_to_db.php`:
   - Iterate over `RECIPE_PROFILES`.
   - Ensure corresponding rows exist in `product_ingredients` and `product_size_prices`.
2. Update `calculate_product_consumption()`:
   - Query `product_ingredients` and `product_size_prices` directly.
   - Remove the ~250 lines of hardcoded arrays from `core/recipe_engine.php`.
3. Allows store managers to tweak recipes (e.g. increase milk from 180ml to 200ml) 
   directly in the Product Management UI without developer intervention.

6. PERFORMANCE & ASSET DELIVERY

--------------------------------------------------------------------------------
6.1 Cache-Busting via Asset Versioning Helper
--------------------------------------------------------------------------------
PROBLEM:
Static asset URLs (`assets/css/reports.css`, `assets/js/modules/reports.js`) can 
be cached aggressively by browsers. When code changes, cashiers can see stale UI 
or broken AJAX calls.

SOLUTION:
Add an asset versioning helper in `core/helpers.php`:
```php
function asset_url(string $path): string {
    $fullPath = __DIR__ . '/../' . ltrim($path, '/');
    $version = file_exists($fullPath) ? filemtime($fullPath) : '1.0';
    return $path . '?v=' . $version;
}
```
In template views:
```html
<link rel="stylesheet" href="<?= asset_url('assets/css/reports.css') ?>">
<script src="<?= asset_url('assets/js/modules/reports.js') ?>"></script>
```
