1. AUTHENTICATION & SESSION MANAGEMENT ENGINE (`core/auth.php`)
--------------------------------------------------------------------------------
- Hardened Session Management:
  * Sessions initialized via `init_session()` with secure cookie settings:
    - `lifetime = 0` (session cookie expires upon browser closure).
    - `httponly = true` (blocks client-side JavaScript from accessing cookies,
      preventing XSS session theft).
    - `samesite = 'Lax'` (mitigates Cross-Site Request Forgery).
    - `secure = true` automatically enabled when running over HTTPS.
  * Session Fixation Defense:
    - Executing `login_user()` calls `session_regenerate_id(true)` immediately upon
      successful credential validation, destroying the old unauthenticated session ID.
  * Real-Time Session Invalidation on Deactivation:
    - `current_user()` re-queries the `users` table on each incoming request.
    - If an administrator marks an account as `inactive` or `pending`, their active
      session is terminated immediately on their very next request or API call,
      responding with `HTTP 401 Unauthorized` and redirecting to `login.php`.
  * Session Cleanup:
    - `logout_user()` unsets all session variables, expires the session cookie,
      and calls `session_destroy()`.

- Cryptographic Password Storage:
  * Password hashing utilizes PHP's native BCRYPT algorithm (`PASSWORD_DEFAULT` with
    cost factor 12).
  * Timing-attack resistant verification via `password_verify()`.
  * Plaintext passwords and password hashes are strictly omitted from all JSON API responses.

- Brute-Force Rate Limiting:
  * Database table `login_attempts` tracks client IP and username attempts.
  * Five (5) consecutive failed login attempts within a 15-minute window automatically
    throttle subsequent requests with `HTTP 429 Too Many Attempts` for 15 minutes.
  * A successful login immediately flushes the failed attempt counter for that IP and username.

- Cross-Site Request Forgery (CSRF) Defense:
  * Generates cryptographically secure 256-bit per-session tokens (`bin2hex(random_bytes(32))`).
  * Injected into the client application via `window.CafeFlowUser.csrf_token`.
  * Client `api()` fetch wrapper automatically attaches `X-CSRF-Token` to all GET, POST,
    and FormData requests.
  * Enforced across all mutating backend endpoints:
    - `api/checkout.php`
    - `api/complete_order.php`
    - `api/products_api.php`
    - `api/inventory_api.php`
    - `api/accounts_api.php`

2. ROLE-BASED ACCESS CONTROL (RBAC) ARCHITECTURE
--------------------------------------------------------------------------------
The system defines two strictly segregated roles:

+---------------------------+-----------------------+-----------------------+
| Module / Capability       | BARISTA               | MANAGER               |
+---------------------------+-----------------------+-----------------------+
| POS / Cashiering Grid     | FULL ACCESS           | STRICTLY NO ACCESS    |
| Live Barista Queue        | FULL ACCESS           | STRICTLY NO ACCESS    |
| Order Checkout API        | FULL ACCESS           | STRICTLY NO ACCESS    |
| Products Catalog Modal    | FULL ACCESS           | STRICTLY NO ACCESS    |
| Products Management API   | FULL ACCESS           | STRICTLY NO ACCESS    |
| Inventory Management      | FULL ACCESS           | FULL ACCESS           |
| Sales Reports & Analytics | VIEW & EXPORT         | VIEW & EXPORT         |
| Account Management        | STRICTLY NO ACCESS    | FULL ACCESS           |
| Manager Self-Demotion     | N/A                   | PROHIBITED (403)      |
| Manager Self-Deactivation | N/A                   | PROHIBITED (403)      |
| Last Manager Deactivation | N/A                   | PROHIBITED (422)      |
+---------------------------+-----------------------+-----------------------+

- Multi-Layer Enforcement:
  * Layer 1 (Server-Side DOM Segregation):
    `index.php` conditionally renders markup based on `$currentRole`:
    - Baristas receive the POS Cashier split-screen and `#productModal`.
    - Managers NEVER receive POS or Product DOM elements; instead, they receive the
      dedicated Manager Workspace Portal (`#managerDashboard`).
    - The Account Management modal (`#accountsModal`) is rendered exclusively for Managers.
  * Layer 2 (Client Navigation & Polling):
    - `showView()` blocks unauthorized view switching with an explicit warning toast.
    - Managers never initiate polling for the POS queue or product catalog.
  * Layer 3 (Backend API Authorization Guards):
    - Every endpoint verifies roles via `require_role('barista')` or `require_role('manager')`.
    - Tampered or direct requests to restricted endpoints are rejected with `HTTP 403 Forbidden`.

- Manager Safety & Self-Protection Rules:
  * A Manager cannot change their own role to Barista (`403 Forbidden`).
  * A Manager cannot deactivate or suspend their own account (`403 Forbidden`).
  * The system prevents deactivating or demoting the last active Manager account (`422`).

- Barista Account Management Removal:
  * Baristas have zero access to Account Management (`api/accounts_api.php` enforces `require_role('manager')`).
  * The "Account Management" shortcut is omitted from the Barista's Profile dropdown.

5. DATABASE SCHEMA MIGRATIONS & SEED DATA
--------------------------------------------------------------------------------
- Automatic Schema Migration in `core/db.php`:
  * Created `users` table:
    - `user_id` INT UNSIGNED AUTO_INCREMENT PRIMARY KEY
    - `full_name` VARCHAR(100) NOT NULL
    - `username` VARCHAR(50) NOT NULL UNIQUE
    - `email` VARCHAR(100) NOT NULL UNIQUE
    - `password_hash` VARCHAR(255) NOT NULL
    - `role` ENUM('barista', 'manager') NOT NULL DEFAULT 'barista'
    - `status` ENUM('active', 'inactive', 'pending') NOT NULL DEFAULT 'active'
    - `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    - `updated_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP
    - `last_login` DATETIME NULL
  * Created `login_attempts` table:
    - `id` INT UNSIGNED AUTO_INCREMENT PRIMARY KEY
    - `ip_address` VARCHAR(45) NOT NULL
    - `username` VARCHAR(50) NOT NULL
    - `attempt_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
    - `success` TINYINT(1) NOT NULL DEFAULT 0
  * Added `cashier_user_id` to `transactions`:
    - Tracks which authenticated Barista processed each customer transaction.
    - Foreign key references `users(user_id)` ON DELETE SET NULL.

- Synchronized Starter Seed Accounts:
  * Barista: `barista` / `barista123` (Full Name: "DK Cafe Barista", Active)
  * Manager: `manager` / `manager123` (Full Name: "Manager", Active)

6. AUTOMATED QA AUDIT & STRESS TESTING REPORT
--------------------------------------------------------------------------------
An automated QA verification runner was built and executed (`scratch/comprehensive_qa_audit.php`):
- Overall Results: 73 / 73 Test Suites Passed (100.0% Success Rate).
- Key Test Categories Verified:
  1. Authentication & Input Fuzzing:
     * Valid username & email sign-ins.
     * Rejection of invalid passwords (401), non-existent users (401), empty inputs (422).
     * Handling of whitespace trimming, 10,000-character payload fuzzing, and unicode characters.
     * Safe rejection of SQL injection (`' OR '1'='1' --`) and XSS (`<script>`) payloads.
     * Rejection of deactivated accounts (403) and pending accounts (403).
     * Brute-force rate limiting: 5 failed attempts triggered HTTP 429.
  2. Session Lifecycle:
     * Verified `HttpOnly` and `SameSite=Lax` cookie properties.
     * Session persistence across requests.
     * Session termination upon logout (invalidated session returned `401 Unauthorized`).
  3. Repeated Stress Testing:
     * 50 continuous automated login/logout cycles alternating Barista and Manager accounts.
     * 0 failures, 0 memory leaks, 0 stale state retentions.
  4. RBAC Permission Checks (100+ checks):
     * All 8 core endpoints tested against Barista and Manager permissions.
     * Manager blocked from POS menu (403), queue (403), products (403), checkout (403),
       and completing orders (403).
     * Manager self-demotion, self-deactivation, and last manager deactivation blocked.
  5. Account Lifecycle & Real-Time Invalidation:
     * Manager created new Barista account.
     * New account authenticated successfully and accessed POS.
     * Manager deactivated the account while its session was live.
     * The very next request from that session was rejected with `401 Unauthorized`.
  6. Anti-CSRF Verification:
     * Mutating calls without `X-CSRF-Token` were rejected with `403 Forbidden` across
       checkout, complete order, products, inventory, and accounts APIs.
     * Valid tokens were accepted without issue.
  7. CafeFlow Core Business Regression:
     * POS order checkout (Cash and GCash) recorded transactions accurately.
     * Cashier ID tracked on transaction records.
     * Order completion in queue deducted raw ingredients and packaging according to recipe.
     * Inventory supplies, low stock alerts, sales summaries, and Excel `.xlsx` exports intact.
     * Headless Chrome verified 0 JavaScript console errors on `login.php` and `index.php`.
